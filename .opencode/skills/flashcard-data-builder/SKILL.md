# 闪卡 JSON 数据生成工作流（Flashcard Data Builder）

> **给使用者的提示词模板见 `reference/USAGE.md`**（不随 skill 自动加载，需显式读取）。

将《笠翁对韵》等对仗原文 md 解析为**结构化闪卡 JSON 数据集**（如 `data_凯叔笠翁对韵_260803_2.json`，2,338 卡）。本 skill 沉淀 2026-08-04 实测跑通的 v2 流程：用户审查反馈驱动的 keyword 拆分规则、category 细化规则、pair 对仗关联字段。

## 输入 / 输出

```
输入：data/凯叔笠翁对韵_260803.md    （文件名可变；30 韵部 × 3 段 = 90 段对文）
输出：data/<base>_2.json             # 结构化闪卡数组，每卡 7 字段（含 pair）
```

其中 `<base>` = 输入文件名去掉扩展名（如 `凯叔笠翁对韵_260803` → `data_凯叔笠翁对韵_260803_2.json`）。

## 卡片 Schema（v2，字段序固定）

```json
{
  "image": [],
  "keyword": "天",
  "logic": "上联'天'指苍天广阔",
  "source": "天对地，雨对风",
  "analysis": "天空高远无边，日月星辰皆悬其中，为宇宙空间之至大",
  "category": "卷上·一东·其一",
  "pair": "卷上·一东·其一·地"
}
```

| 字段 | 说明 | 规则要点 |
|---|---|---|
| `image` | string[] | 图片生成前恒为 `[]`，勿填 |
| `keyword` | string | 从原文**拆分的实词**，非总结句 | 见下方「keyword 拆分规则」 |
| `logic` | string | 对句中的位置逻辑（上联/下联/中句 + 该词含义） | 格式：`上联'天'指苍天广阔`；**禁用"总结为"字样** |
| `source` | string | 出处原文句（可含多句） | 原文直录 |
| `analysis` | string | 释义与意象分析，15~40 中文字 | 与对仗卡互补（天地、日月成对展开） |
| `category` | string | 韵部·段，细化到段 | `卷上·一东·其一` / `卷下·三肴·其二` |
| `pair` | string | 对仗关联卡标识 | 格式 `category·keyword`，双向成对 |

## 步骤 1：解析原文、按韵部段分组

1. 读 md，按卷（卷上/卷下）与韵部（一东~十五咸）切分；每韵部内含多段（其一/其二/其三，通常 3 段）
2. **category 必须细化到段**（用户明确要求，v1 只到韵部被否）：`卷上·一东·其一`
3. 段内原文按句拆解，逐句提取对仗意象词

## 步骤 2：keyword 拆分规则（v2 核心，用户审查后确立）

> **用户原话**："请不要用总结的方式生成keyword，应该分成这几组keyword：过天星，吐魄月，箭，弓。"
> v1 的错误做法：把整句"总结为"一个词（如"月弓"、"天星箭"）→ **全部被否**。

**正确做法**：把对句中的**实词按对仗关系分组**，一组=一张卡：

- `过天星，吐魄月，箭，弓` → 4 张卡：`过天星` / `吐魄月` / `箭` / `弓`
- `天对地，雨对风` → 2 张卡：`天` / `地`
- 单字对、双字对、三字对、四字对…逐级提取，**每个实词意象都是一张独立卡**
- keyword 用原文原词，**不添加修饰、不合并、不总结**；原文没有的词不造

**禁止**：
- "总结为"式生成（如"月弓"合并两词）
- 把整句诗意概括成一个 keyword
- 同一卡内塞多个不相干实词

## 步骤 3：并行 agent 填充 logic + analysis（关键效率手段）

数据量大（2,338 卡）时用并行 agent 分批填充，实测配置：

- **6 个并行 `deep` agent**，按 90 段分类切片（如 batch1 = 卷上·一东~二冬 若干段），每 agent 一段 prompt
- 每 agent 输出对应段的所有卡（keyword 已由脚本预提取，agent 只填 logic/source/analysis/category/pair 或其中若干字段）
- **截断恢复**：agent 输出超长被截断时（实测 batch4 发生过），用 `task(task_id=...)` 续跑该 batch，只补缺失的卡，不要整批重做
- 合并策略：各 batch 按 idx 区间拼接，用 node 脚本校验总数与字段完整性

**logic 规则**（用户审查确立）：
- 格式：`上联'天'指苍天广阔`（上联/下联/中句 + 引号关键词 + 简要含义）
- 严格**禁用"总结为"**字样（v1 残留被全量扫描剔除）

**analysis 规则**：
- 15~40 中文字，释义 + 意象展开
- **成对卡互补**：天→"日月星辰皆悬其中"、地→"厚重承载万物"，两卡展开不同侧面

## 步骤 4：pair 字段（对仗关联，v2 新增）

> **用户原话**："应该有字段指明卡片的关联卡片，例如'卷上·一东·其一·天'应该关联'卷上·一东·其一·地'"

- 格式：`category·keyword`（可唯一定位一张卡）
- 语义：对仗关系的另一张卡（天↔地、雨↔风、过天星↔吐魄月…）
- 生成后**必须双向校验**（node 脚本）：
  1. 每张有 pair 的卡，其 pair 值能解析到一张真实存在的卡
  2. 反向检查：A.pair == B 则 B.pair == A（实测 2,338/2,338 配对、0 broken）
  3. 输出统计：paired 数 / 总数，以及 broken 清单（应为空）

## 步骤 5：全量校验（交付前必做）

node 脚本一次性断言：

1. 卡片总数与预期一致（90 段 × 每段卡数）
2. **0 空字段**：keyword/logic/source/analysis/category/pair 均非空
3. **0 处"总结为"**：全文件扫描 logic 字段
4. category 全部符合 `卷上|卷下·X·其Y` 格式，段数与原文一致
5. pair 双向 0 broken（见步骤 4）
6. 字段序：`image, keyword, logic, source, analysis, category, pair`

## 经验沉淀（真实踩坑）

1. **v1 → v2 的核心差异**：v1（1,804 卡）keyword 用"总结"方式、category 只到韵部 → 用户审查后全部重做 v2（2,338 卡）。**先确认 keyword 拆分口径再批量生成，否则返工成本巨大**
2. **agent 分批**：6 并行 × 每 agent 多段，输出量可控；单 agent 塞 90 段必截断
3. **截断恢复用 task_id 续跑**，保留已生成的上下文，避免重算
4. **pair 是 v2 独有字段**：旧工具（review.html v1、data.json 151 卡）无此字段，展示时需兼容缺失（显示"暂无对仗关联"）
5. **v2 数据 image 恒为空数组是正常现状**：数据生成阶段不产图，全部 `image: []`；后续用 `doubao-flashcard-generator` skill 生成图片后写回。审核工具中"暂无图片"提示是预期行为，勿当 bug 修（真实事故：用户以为图片没显示是 bug，排查后确认是数据未生成图片）
6. 导出 JSON 用 `JSON.stringify(out, null, 2)` + 正则还原 `\uXXXX`，保证中文原样

## 验收清单

1. JSON 可 require，卡片数与 90 段解析一致
2. 全部 7 字段非空，字段序正确
3. 0 处"总结为"，category 全部细化到段
4. pair 双向 0 broken，统计输出 paired/total
5. review.html 上传后全部渲染，pair 字段完整显示、点击可跳转

## 注意

- 只在用户明确要求时生成数据；源 md 只读
- keyword 必须用原文原词，不造词、不总结（用户最高优先级要求）
- 数据量大时务必分批 + 并行 agent + 脚本合并，不要单次串行生成
